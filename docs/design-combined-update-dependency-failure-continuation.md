# 组合更新中依赖失败后的文档续跑设计

## 背景

组合自动更新 Runner 依次调用依赖更新与增量文档更新 Agent。原有 Prompt 将依赖阶段的 `FAILED` 和 `BLOCKED` 都视为整条流程终止条件，即使依赖 Agent 没有创建提交且工作区能够恢复到原始合并后基线，也不会继续处理原始 PR / MR 引起的文档变化。

依赖更新失败只说明本轮依赖升级无法安全交付，不代表原始变更请求无需更新文档。两类任务共用分支和最终 PR / MR，但业务判断应允许部分独立完成。

## 目标

- 依赖阶段发生可清理的业务失败时，恢复组合分支后继续文档阶段。
- `BLOCKED`、目标分支漂移、状态协议异常和无法验证的清理仍然终止整条流程。
- 文档 Agent 始终从可验证的固定提交开始，不继承失败依赖更新的文件、提交或远程分支状态。
- 最终结果明确区分正常完成、部分完成、失败和阻塞。

## 状态语义

依赖子 Agent 的结果按以下方式处理：

- `UPDATED_AND_PUSHED`：校验依赖提交及远程分支，文档任务起始 SHA 为依赖提交 SHA。
- `NO_DEPENDENCY_UPDATE`：确认没有提交、推送或工作区修改，文档任务起始 SHA 为原始合并后 SHA。
- `FAILED`：保存依赖失败原因，执行依赖阶段恢复。恢复成功后文档任务起始 SHA 为原始合并后 SHA，并继续调用文档 Agent；恢复失败则终止整条流程。
- `BLOCKED`：说明依赖阶段缺少可靠执行条件，不继续文档阶段。

未知状态、结构校验失败、目标分支漂移和平台事实无法确认不属于可降级业务失败，必须终止。

## 依赖阶段恢复

恢复过程只作用于经过严格校验的本次组合分支和本流程产生的状态：

1. 保存依赖 Agent 的原始失败原因和已发生写操作。
2. 关闭并核验同名未合并 PR / MR，删除并核验同名远程组合分支。
3. 丢弃本流程产生的已跟踪修改，只删除能够确认由本流程创建的未跟踪路径。
4. 切换到原始合并后 SHA 的 detached HEAD，删除本地同名组合分支。
5. 刷新并确认目标分支仍等于 `TARGET_HEAD_AT_START`。
6. 从原始合并后 SHA 重新创建同名本地组合分支，确认 HEAD、暂存区、工作区和远程分支状态均干净。

任何一步无法完成或无法可靠核验时，不得继续文档阶段。

## 文档阶段与最终交付

依赖失败恢复成功后，文档影响范围为：

```text
MR 合并前目标分支 SHA..MR 合并后目标分支 SHA
```

文档 Agent 有更新时，可以形成项目原有协议已经允许的单一提交历史：

```text
<合并后 SHA> -> doc(auto-update)
```

该提交仍通过唯一的 `auto-update` PR / MR 交付并接受平台门禁。文档无需更新时不创建空分支或空 PR / MR。

只要依赖阶段曾返回 `FAILED`，最终报告必须标记为“部分完成”，同时保留依赖失败原因、恢复证据以及文档阶段的实际结果；不得把文档成功描述成依赖更新成功。

## 非目标

- 不修改依赖更新 Agent 对版本选择、验证、提交或推送的规则。
- 不允许在依赖验证失败后提交部分依赖更新。
- 不把 `BLOCKED` 自动降级成可以忽略的业务结果。
- 不改变文档更新 Agent 的输入字段和结构化输出协议。
