# 审核 CI 仅校验当前源提交

## 背景与目标

通用审核此前要求合并结果类 CI 同时匹配本轮源提交和目标提交。目标分支在远端 CI 成功后继续更新时，普通 PR / MR 工作流不一定重新触发，审核 Agent 因此把成功结果视为当前组合的验证缺口，提前停止代码与设计一致性审核。

本次统一 GitHub 与 GitLab 的审核规则：本轮有效的本地或远端 CI 明确失败就终止；成功结果只要求可靠关联当前源提交，不再检查 CI 执行时的目标提交，也不根据目标分支更新将成功结果判为过期。

## 行为边界

- `REVIEW_HEAD_SHA` 继续固定为运行上下文的源提交。源提交发生变化或只有其他源版本的成功结果时，不能复用旧结果。
- `REVIEW_TARGET_SHA` 继续作为代码、设计与目标分支语义一致性审核的不可变基准。审核期间源或目标真实 ref 漂移，仍按原规则结束，不评论、不合并。
- 普通源分支 CI 与 merged-results、test merge、merge queue 等合并结果 CI 使用同一源提交关联要求。关联由可信平台元数据确认，不要求合并提交 SHA 与源 SHA 字面相等，也不追查目标父提交或 checkout 日志来判断 CI 新鲜度。
- 当前源版本的本地 Preflight 或远端有效 CI 明确失败，停止继续审核；尚未审核完的范围必须标为部分。非必要 GitHub 检查的明确失败也不能因为不属于分支保护要求而忽略。
- 运行中、未知、查询失败和源关联无法确认都不视为成功，也不能仅因没有检查项就断言 CI 失败。确认没有 CI 的既有规则、等待截止时间和超时保留成果规则不变。
- CI 成功后继续完整代码、设计与语义一致性审核，不要求为当前目标版本重跑 CI，不在最终评论中把旧目标组合缺少验证列为阻断原因，也不宣称该成功证明当前合并组合已测试。
- 审批、分支保护、讨论解决、合并队列等平台实际门禁仍需满足；不额外增加平台未要求的 CI 目标新鲜度门槛，不绕过已有门禁。

## 实现范围

调整通用审核 Prompt 的核心原则、不可变基准、CI 状态判断、终止策略、结论状态机和最终通过条件；同步两种运行器共享的 CI 工具说明。等待器继续只校验源 SHA：GitLab 的 `head_pipeline.sha` 若是临时合并提交，通过固定项目内的 Commit API 校验该提交 ID 和第二个源父提交；不查询目标 ref、不比较目标父版本，也不读取 checkout 日志。非双父提交、仅目标父节点匹配、旧源或无效元数据均不能通过。GitHub 的源提交检查查询和本地 Preflight 编排失败阻断行为保持不变。

GitLab 合并结果流水线使用临时合并提交，提交 API 提供 `id` 与 `parent_ids`；GitLab 的合并服务按目标、源顺序解析两个父节点。参考 [合并结果流水线](https://docs.gitlab.com/ci/pipelines/merged_results_pipelines/)、[提交 API](https://docs.gitlab.com/api/commits/#get-a-single-commit) 和 [合并引用服务源码](https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/services/merge_requests/merge_to_ref_service.rb)。无法取得可靠源关联证据时继续按未知状态处理，不放行。

同步现行设计与使用文档，新增模板渲染、真实运行输入和跨平台只读等待回归。不会修改本机配置、历史审核评论、真实仓库 CI 工作流，也不会自动重放任务或重跑远端 CI。
