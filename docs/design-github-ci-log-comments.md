# GitHub 本地 CI 报告与完整日志

GitHub 的本地 CI 状态不再引用管理员后台地址。终态先回写，暂用关联 PR 的平台地址；独立日志队列随后把完整日志合并到 PR 内的主评论，并补充状态入口。失败时直接更新已有失败报告；成功或关闭失败摘要时只发布一条运行报告。

完整运行记录沿用 GitLab 的导出与跨块凭据脱敏。先按实际评论字节数与诊断空间判断能否整份内嵌；能放下时只有一条评论，失败摘要、诊断和完整日志各自折叠。只在合并后超出单条上限时发布日志续页，目录放在主评论中；极长目录才继续分组。已内嵌完整日志时缩短重复的末尾摘要，完整原始输出仍保留。评论按运行 ID、执行尝试与分段序号托管，部分发布失败后可恢复。所有链接来自 GitHub 评论 API 的原生地址，保留仓库访问控制。

合并材料存入当前执行尝试的日志发布记录，在主评论锁内与最新诊断一起重建正文；日志与诊断以任意顺序完成均不能互相覆盖。主评论合并成功后才删除同次执行多余的旧版日志、目录评论，不触碰人工评论、其他运行或其他 Agent 的评论。基础设施异常不能因此新建代码失败评论。

GitHub 合并判断和含完整日志的诊断正文共同使用托管评论的 60 KiB 上限，不再使用普通失败摘要的 54 KiB 预算。诊断进入终态后刷新一次独立发布任务，依据实际报告重新合并；失败、取消或缺失 Agent 时也释放不再需要的预留空间。发布记录按排版版本和诊断材料计算复用指纹，旧分段结果不能直接跳过这次合并。队列刷新推进版本号，旧任务只允许结束自己领取的版本，避免诊断恰好在日志发布中完成时丢失刷新请求。重排不执行 CI，也不重新运行诊断 Agent。

传输继续使用持久化后台队列、资源租约和有限重试。旧 Head、旧运行及旧执行尝试不能补写最新状态或重建活动失败评论。GitLab 仍上传原项目附件；日志发布失败不改写真实 CI 结果，不回退到管理后台链接。新提交或新的真实 CI 结果继续按原生命周期发布，同一次 CI 的异步结果只补充主评论。
