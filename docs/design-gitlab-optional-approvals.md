# GitLab 社区版可选审批兼容设计

## 问题与目标

GitLab 社区版的 MR 审批接口中，`approved: false` 仅表示尚无人提交可选批准，不表示存在未满足的强制审批。社区版不提供高级审批规则接口，不能将这些接口的 404 与无人批准组合成审核阻断原因。

本次按平台实际版本解释审批语义，不修改项目审批设置，不代替用户执行批准，也不把批准人数改成虚构的已满足状态。

## 数据流与判定

- GitLab Provider 在单个客户端生命周期内只读查询一次 `GET /version`，并发扫描共用查询结果。仅接受真实布尔值 `enterprise`；缺失、格式异常、权限错误和请求失败都保留未知版本，不影响 MR 快照读取。
- 实例信息放入快照 `raw.gitlab_instance`，不参与规范化快照比较，不因版本探测产生新的业务事件，无需数据库迁移。
- 执行器为 GitLab 根 Agent 增加 `mr.approval_context`：平台版本、可选/必需/未知审批要求、真实 `approved` 和非负整数审批数量。只传白名单字段，不传原始响应、审批者信息或评论。
- 仅当可信平台明确返回 `enterprise: false`，且没有 `not_approved` 或正数审批要求等矛盾证据时，才能标记为可选审批。404、空规则或 `approved: false` 本身均不足以识别社区版。
- 企业版继续核验真实审批规则、所需数量及批准状态；未知版本不能默认无需审批。旧记录缺少版本信息时，Agent 可通过只读平台版本接口补充核验。

## 审核边界

通用审核 Prompt 在仅审核与自动合并两种模式下均明确：已确认社区版且无强制审批证据时，`approved: false`、批准人数为零及高级规则接口不支持不构成阻断，不再反复查询同义接口。结论可写“人工审批：不适用（社区版可选审批；当前无人批准）”，不得伪称用户已经批准。

平台明确的 `not_approved`、冲突、Draft、讨论未解决、分支保护或其他合并门禁仍优先处理；GitHub 行为不变。CI 失败终止、成功仅校验源提交、审核自身源/目标 SHA 漂移保护及禁止越权批准/合并均保持不变。

参考：[审批 API 的社区版与企业版语义](https://docs.gitlab.com/api/merge_request_approvals/#retrieve-approval-state-for-a-merge-request)、[可选与必需审批](https://docs.gitlab.com/user/project/merge_requests/approvals/)。

## 生效与范围

新启动的审核使用更新后的 Prompt；新扫描的快照携带实例信息。旧快照保持兼容，未知能力不得默认为可选。不修改本机配置、不重放审核、不改写历史评论，也不在此次代码任务中重启服务。
