# GitHub / GitLab Preflight CI 门禁

## 职责边界

通用引擎负责准确检出 MR / PR Head、隔离执行、超时与日志控制、结果幂等、平台 Commit Status 回写，以及成功后启动明确要求 CI 的 Review Agent。接入仓库负责维护实际 CI 脚本、工具依赖、审核规则和平台合并门禁。

## 执行与幂等

仓库启用 `preflight` 只代表具备本地 CI 能力。编排器仅在匹配规则配置 `run_preflight: true`、仓库启用 CI 且变更请求仍处于打开状态时执行门禁。规则要求 CI 但仓库未启用或未配置时直接启动 Agent，不报错；MR / PR 已关闭或合并时也跳过门禁。规则选择全部仓库时，不要求所有启用仓库都配置 CI。

编排器向事件 Agent 提供独立的 `local_preflight` 摘要。`passed` 绑定本次成功结果的仓库、编号及源 SHA，附带运行 ID 和复用标记；`skipped` 按实际规则说明跳过原因，不伪装为通过。摘要不含原始日志，随可信调用上下文传给子 Agent，与 CI 失败诊断的 `preflight_run_id` 授权分离。审核模型只按摘要报告后台执行事实，不查询、补跑或重新判断本地门禁；缺少摘要也不增加阻断条件。模型额外专项测试单独报告，环境限制不覆盖后台成功结果，真实可复现的代码问题仍按审核标准处理。远端 CI 检查和平台实际门禁不变，详见 [本地门禁上下文设计](design-review-local-ci-context.md)。

同一批次中未要求 CI 的 Agent 会立即启动，不等待 Preflight。要求 CI 的规则共享以仓库 ID、PR 编号、Head SHA 和完整配置 revision 生成的幂等结果。`success`、`failure` 与 `timed_out` 是可复用的本地终态；Git、进程启动或清理故障产生的 `error` 只影响要求 CI 的事件路径，并按事件重试额度再次执行。基础设施异常耗尽自动重试后，扫描事件继续复用该终态以避免无限运行；管理员新建的手动事件会把旧运行保留为历史记录，并为同一幂等键原子换入一条全新运行和完整重试额度。新运行随后成为同一 Head 与配置的当前可复用结果。

执行器先更新 MR / PR 引用并创建独立 detached worktree，校验实际 Head SHA、初始化 submodule；精确工作区准备成功后才写入 `pending` Commit Status，并按参数数组顺序执行步骤。GitLab 状态写入 MR 的源项目与源分支，避免把外部作业放到错误的流水线；同一 SHA/ref 写入发生临时 409 冲突时最多重试两次。命令不经过 shell；单步超时同时受总超时约束，首个非零退出码停止后续步骤。日志按 `max_output_bytes` 保留最新内容。Preflight worktree 与 Agent 运行 clone/worktree 相互独立，均不修改基础仓库。

`cache_enabled: true` 时，依赖下载缓存按仓库稳定身份隔离并跨分支共享，避免同一仓库的不同 MR / PR 重复下载；临时 worktree、HOME 与安装目录不共享。系统会为常见 Python、Node.js、Rust、Go、Java、.NET、PHP 和浏览器工具注入其标准缓存变量。仓库详情还可以手动执行远端默认分支最新提交，用于提前填充缓存；手动运行不设 CI 步骤总限时，但可以取消，且不会触发 Agent 或发布 MR / PR Commit Status。

所有新运行都会把 Git 准备阶段、当前步骤状态及合并后的 stdout/stderr 按游标写入实时日志。仓库手动执行入口、运行概览事件详情和“运行与日志”页复用同一详情视图；终态仍额外固化有界完整输出，旧记录没有实时日志时自动回退到终态输出。

本地命令终态和 Commit Status 发布标记分别持久化。终态已经生成但平台回写失败时，后续重试只补发状态，不重新执行仓库命令。

开启失败评论后，同一 MR / PR 与 `status_context` 只保留一条活动 Preflight 评论。新的真实失败或超时会先删除旧评论，再在时间线底部创建本轮评论；相同 CI 结果被其他事件复用时不会反复刷新，只有本地映射缺失时才补建。当前最新源版本的真实或复用成功结果都会清理该槽位全部历史代次失败评论，历史旧代次成功不触碰新 Head 评论。该生命周期只适用于 Preflight，Agent 托管评论仍按源版本代次保留审核历史。

GitLab 自动 MR 的本地 CI 结束后，会将完整运行记录上传为该项目的 `.log` 附件，包括准备过程、步骤命令、时间、退出码与完整保留输出。`teamwork/local-ci` 终态入口和失败评论均使用附件链接；运行中暂不提供最终日志链接，不再跳转管理员后台。GitHub 当前状态入口保持原有行为。

附件按运行 ID 与执行尝试次数去重，成功后跨重启与状态补发复用。单次上传阶段总限时 30 秒，临时网络或服务故障最多尝试三次，权限不足和文件过大立即报错。上传故障在本地 CI 详情独立显示，不改变 CI 判定。附件上传前执行跨日志块凭据脱敏；旧记录只有末尾摘要时会明确注明日志不完整。远端附件由 GitLab 项目管理，本地历史清理不自动删除它们。

## 状态映射

- `success`：写入平台 `success`，继续启动要求 CI 的 Review Agent。
- `failure`：GitHub 写入 `failure`、GitLab 写入 `failed`，正常结束要求 CI 的规则路径；不影响同批次未要求 CI 的 Agent。
- `timed_out`：按代码失败处理并写入平台失败状态，只阻断要求 CI 的规则。
- `error`：不写入终态 Commit Status，也不发布普通失败摘要；只让要求 CI 的事件路径失败并按 `event_retry_count` 重试。开启失败诊断后，重试耗尽可单独生成并按失败评论设置同步诊断报告。

启用门禁的仓库会自动产生首次 `change_request.discovered` 事件，不受全局 `scanner.emit_initial_events` 开关影响。GitHub 可在 Ruleset 中把 `status_context`（默认 `teamwork/local-ci`）设为 required status check。GitLab 状态以同名外部作业参与源提交的流水线；若需在平台阻止失败合并，可启用项目的“Pipelines must succeed”。GitLab 若同时产生分支与 MR 流水线，应检查状态是否关联到目标 MR 显示的流水线，避免平台选择其他流水线导致门禁未生效。

## 自动失败诊断

仓库详情的本地 CI 配置支持 `failure_diagnosis_enabled`（默认开启）和 `failure_diagnosis_agent`（默认 `ci-failure-diagnoser`）。新启用本地 CI 时默认启用失败诊断；已启用 CI 但未配置诊断开关的旧仓库，也按开启处理。明确配置 `false` 时保持关闭，切换 CI 开关不会覆盖这一选择。本地 CI 未启用时不会单独启动诊断。自动 MR/PR CI 的 `failure`、`timed_out` 以及重试耗尽的 `error` 会启动独立诊断 Agent。要求 CI 的正常审核仍然终止，不因诊断报告完成而放行。取消、被新提交取代以及手动默认分支 CI 不触发诊断。

首次加载提供内置 `ci-failure-diagnoser`，在 Agent 页可修改模型、effort、提示词、轮次和超时，也可以删除。默认最多 32 轮、总时限 600 秒，另外沿用空闲超时和取消控制。配置中的 `builtin_agents_version` 记录模板已初始化，删除后重启不会恢复。重命名会同步仓库引用；删除则保留引用，后续 CI 详情显示“诊断已跳过”及指定 Agent 不存在的原因，不回退到其他 Agent。

诊断使用模型工具循环，只提供完整保留日志的分页搜索、固定失败 SHA 的 Git 对象读取，以及本轮长工具结果的补读。不会执行仓库准备脚本、安装依赖、重跑测试或修改源码。源码对象已清理或不可读取时，报告必须说明证据限制。日志与报告使用现有凭据脱敏机制。

报告和诊断状态单独持久化在 CI 详情，支持复制 Markdown、查看正常 Agent 运行记录和取消诊断。每个 CI 运行原子占位一次；复用同一失败结果不重复调用模型。诊断失败、超时或服务中断可见，但不改变 CI 原始结论。

同时开启 `publish_failure_comment` 时，服务端在同一条失败评论中保留状态、Head SHA、失败步骤、退出码、错误信息和原始末尾输出，并追加默认折叠的“CI 失败诊断报告”。“末尾输出”也默认折叠，诊断展开后按 Markdown 展示。GitHub 与 GitLab 使用相同格式，评论不附带仅管理员可访问的项目 UI 链接。超过评论长度限制时仅截取报告并注明截断，完整报告保存在管理后台；追加报告不会挤掉原有日志。评论写回在槽位锁内核对最新 CI 及源版本，避免迟到报告覆盖新结果，或在成功清理后重建旧失败评论。评论同步失败会在诊断报告区单独显示，完整报告仍保留。

## 凭据与安全边界

CI 子进程只隐式继承工具运行所需的 PATH、临时目录、语言、证书、代理和缓存变量，并注入 `CI=true`；`HOME` 指向一次性空目录。当前仓库解析出的 Provider Token 默认也会进入仓库 CI，管理员关闭对应变量的“进入进程”后才移除。Codex/OpenAI 模型凭据不会通过该开关进入被测代码。把 Provider Token 暴露给 CI 意味着仓库代码能够读取并外传该凭据，因此该默认面向可信内部仓库，并应为每个仓库配置满足任务所需权限的独立 Token；检查不可信代码时应关闭进程暴露或使用更强隔离。

临时 worktree 与环境过滤只用于隔离工作目录和避免凭据意外继承，不是容器或操作系统级安全边界。当前威胁模型仅覆盖可信内部成员提交的 PR；检查 fork 或其他不可信代码前，应迁移到独立 UID、容器或虚拟机，并限制挂载、进程与网络。

GitHub 和 GitLab 均支持状态回写；GitLab 使用 `/projects/:id/statuses/:sha` 接口，`status_context` 对应外部作业名称，失败状态转换为 `failed`。每个步骤是一条不经过 shell 的参数数组命令；简单检查可以直接配置程序与参数，复杂流程可以调用目标仓库维护的 Bash、Python 或其他脚本。原生 Windows 可以直接执行 Python、Node.js、PowerShell 等程序；配置为 `bash ci/preflight.sh` 的步骤仍要求 Git Bash、WSL2 或其他可用的 Bash。仓库详情提供步骤名称、执行程序、逐项参数和超时配置，触发规则详情负责选择是否使用仓库 CI。
