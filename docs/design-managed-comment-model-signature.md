# 托管评论模型签名设计

## 背景

Agent 通过 `publish_comment` 发布托管顶层评论时，远端评论目前只包含模型生成的正文。管理员无法从 PR / MR 时间线直接确认某一轮评论由哪个模型和推理强度产生，也不能可靠地区分模型切换前后的审核结果。

模型签名属于 Teamwork 的运行审计信息，不应依赖 Prompt 要求模型自行填写。模型可能漏写、误写，或把当前配置误认为本次实际配置；服务端必须使用运行创建时已经固化的模型快照统一生成签名。

## 配置与交互

Agent 新增 `managed_comment_model_signature` 布尔配置，默认关闭。管理界面在“按源版本托管顶层评论”区块增加“附加模型签名”开关；托管评论关闭时该开关不可操作，但保留原配置值，重新开启托管评论后继续生效。

模型签名只影响 Agent 通过 `publish_comment` 发布或更新的托管评论。Preflight / CI 的确定性失败评论没有模型运行，不追加模型签名。

## 签名来源

`publish_comment` 使用可信调用上下文中的 `run_id` 读取 `agent_runs.model_snapshot`。该快照在根 Agent 或 sub-agent 本轮运行开始时保存，包含实际解析后的模型、推理强度及其来源，不读取发布时可能已经变化的全局或 Agent 配置。

- 有明确模型且有推理强度：`gpt-5.6-sol (high)`。
- 有明确模型但没有推理强度：`deepseek-v4-pro`。
- 无法解析具体模型：`Codex 账号默认（未记录具体模型）`。

模型和推理强度在写入 Markdown 前规范为单行文本并转义反引号，避免配置值破坏评论结构。

## 评论格式与生命周期

签名由服务端追加到正文末尾：

```markdown
---
_模型：`gpt-5.6-sol (high)`_
```

签名是最终评论正文的一部分，必须在非空校验、60 KiB 大小校验和内容哈希计算之前完成拼接。因此模型或推理强度发生变化时，即使模型生成正文完全相同，本轮发布也会更新当前源版本代次的评论。

该功能不改变托管评论的源版本规则：目标分支变化继续更新当前评论，源分支产生新提交或 force-push 后继续在新代次创建评论，人工删除远端评论后仍只在下一次实际发布时重建。
